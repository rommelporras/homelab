# ship

Create a versioned release for this homelab repo. Work through each step in order.
Do NOT proceed past Step 7 until the user explicitly confirms.

**Prerequisite:** `gh` CLI must be installed and authenticated (`gh auth status`).

## Usage

```
ship                      - Auto-determine version from commits
ship v0.1.0               - Use explicit version, auto-generate title
ship v0.1.0 "Title Here"  - Use explicit version AND title
```

## Step 1 - Check current state

```bash
git branch --show-current   # Must be on main
git status                  # Must be clean working tree
git log --oneline -5        # Recent commits
git describe --tags --abbrev=0 2>/dev/null || echo "No tags yet"
```

- Must be on `main` branch - abort if on any other branch
- Working tree must be clean - abort if dirty (uncommitted changes)

## Step 2 - Remote tag collision check

Fetch latest tags from origin and verify the target version does not already exist:

```bash
git fetch origin --tags
git tag -l "v<VERSION>"
```

If the tag already exists:
- ABORT immediately
- Show: `Error: Tag v<VERSION> already exists. Check https://github.com/rommelporras/homelab/releases`
- Suggest the next available version

## Step 3 - Determine version and title

The full release title is always: `v<VERSION> - <Short Title>`
(regular hyphen, NOT em dash).

**If user provided version and title** (e.g., `ship v0.1.0 "Project Setup"`):
- Use the provided version
- Full title: `v0.1.0 - Project Setup`

**If user provided version only** (e.g., `ship v0.1.0`):
- Use the provided version
- Auto-generate Short Title from commit analysis
- Full title: `v0.1.0 - <Auto-generated Title>`

**If no version provided** (`ship`):
- Find last tag: `git describe --tags --abbrev=0`
- Analyze commits since last tag: `git log <last-tag>..HEAD --oneline`
- Auto-bump based on commit types:
  - `feat:` present -> minor bump (v0.1.0 -> v0.2.0)
  - `fix:` only -> patch bump (v0.1.0 -> v0.1.1)
  - `BREAKING CHANGE` in any commit -> major bump (v0.1.0 -> v1.0.0)
  - `docs:`, `chore:` only -> patch bump
- Auto-generate Short Title from commit analysis

**First release** (no previous tags): default to `v0.1.0` unless user specifies.

## Step 4 - Pre-release checks

Run all checks and collect results before reporting. Show them all together in Step 7.

**Phase plan check** - find the plan for this version:
```bash
grep -rl "Target.*v<VERSION>\|release.*v<VERSION>" docs/todo/ --include="*.md" 2>/dev/null | grep -v completed/
grep -rl "Target.*v<VERSION>\|release.*v<VERSION>" docs/todo/completed/ --include="*.md" 2>/dev/null
```

If a matching plan is found, read it and check:
- Status line contains "Complete" (not "In Progress" or "pending release")
- Release checkbox is checked: `- [x] Release v<VERSION>` (not `- [ ]`)
- All other task checkboxes are checked

If any items are unchecked or status is not "Complete": WARN and show which items remain.

**Orphaned active plans check** - scan `docs/todo/` (not `completed/`) for:
- Unchecked release boxes: `- [ ] Release` patterns
- "pending release" or "In Progress" status strings
If found and they DON'T match this release version: INFO (not blocking, just notify).

**VERSIONS.md check** - read `VERSIONS.md` and check the `Last Updated` date:
```bash
head -5 VERSIONS.md
```
If older than 7 days: WARN "VERSIONS.md last updated on <date>. Should it be updated before release?"

**CHANGELOG check** - this project's changelog is at `docs/reference/CHANGELOG.md`.
Format: `## Month DD, YYYY - Title (vX.X.X)` (regular hyphen, NOT em dash).
```bash
grep "v<VERSION>" docs/reference/CHANGELOG.md
```
- If found: good - use its `### Summary` and `### Changes` sections for release notes
- If not found: WARN "No CHANGELOG entry found for v<VERSION> in docs/reference/CHANGELOG.md.
  This should be written as part of the docs commit before releasing."
- Do NOT auto-create a CHANGELOG entry - the format is custom and written manually.

If any warnings were raised, present them all together in Step 7 before confirming.

## Step 5 - Analyze changes for release notes

Do BOTH - read the CHANGELOG AND analyze commits. Cross-reference them.

**Read `docs/reference/CHANGELOG.md`** for the matching version entry:
- Read `### Summary` - use as the basis for `## Summary` in GitHub release notes
- Read `### Changes` table - use rows for `## What's Included` bullets
- Read `### Key Design Decisions` and `### Gotchas` - surface important ones

**Analyze commits** (`git log <last-tag>..HEAD --oneline`):
- Group by type: `infra:`, `fix:`, `docs:`, `feat:`, `chore:`
- Identify anything in commits NOT covered in the CHANGELOG (post-release fixes,
  tooling changes, doc-only work) - include these in `## What's Included`

Combine both sources. The CHANGELOG captures planned work; commits capture everything
including fixes and polish applied after initial implementation.

## Step 6 - Write release notes

**Tag annotation format:**
```
v<VERSION> - <Short Title>

<One sentence summary of this release>

<Category 1>:
- Specific item
- Specific item

<Category 2>:
- Specific item
```

**GitHub release format** (use CHANGELOG entry when available):

```markdown
## Summary
<From docs/reference/CHANGELOG.md ### Summary - one paragraph with context and outcome.
If no CHANGELOG entry, write a paragraph explaining what this release contains.>

## What's Included

### <Meaningful Category - e.g. "HashiCorp Vault", "Observability", "Bug Fixes">
- **Feature name** - what it does and why it matters
- **Another item** - brief description

### <Another Category>
- Item with context

Full details: [CHANGELOG](https://github.com/rommelporras/homelab/blob/main/docs/reference/CHANGELOG.md)
```

Rules:
- `## Summary` is required - always a paragraph, never a bullet list
- Categories reflect what was actually built, not generic commit types (no feat/fix/docs)
- Do NOT include a `## Commits` section - GitHub shows the diff automatically
- The CHANGELOG link is required at the bottom
- No em dashes anywhere - not in tag annotations, release notes, or any generated text
- Title format: always `v<VERSION> - <Short Title>` with a regular hyphen

## Step 7 - Show release plan and confirm

Present the full plan and WAIT for user confirmation before doing anything:

```
Release Plan:
- Version: v0.X.0
- Title: "v0.X.0 - <Short Title>"
- Commits: <N> since <last-tag>
- Will push to: origin/main
- Will create: Annotated tag v<VERSION>
- Will create: GitHub release

Pre-release checks:
- Remote tag collision: (result)
- Phase plan status: (result)
- VERSIONS.md: (result)
- CHANGELOG: (result)

Proceed with release? (waiting for confirmation)
```

Do NOT proceed until the user explicitly confirms with "yes", "proceed", "go", or similar.

## Step 8 - Execute release

Only run after explicit user confirmation in Step 7.

**Step A - Create the annotated tag:**
```bash
git tag -a v<VERSION> -m "<tag annotation text>"
```

**Step B - Push commits and tag:**

Tell the user:
"Please run these two commands in your terminal to push commits and the tag:

  git push origin main
  git push origin v<VERSION>

Confirm when both have succeeded."

Wait for the user to confirm both pushes succeeded before continuing to Step C.

**Step C - Create GitHub release** (run after push is confirmed):
```bash
gh release create v<VERSION> \
  --title "v<VERSION> - <Short Title>" \
  --notes "<release notes markdown>"
```

## Step 9 - Report results

```
Release Complete:
- Version: v<VERSION>
- Tag: v<VERSION> on main
- GitHub remote: main + tag pushed
- GitHub release: <URL from gh output>
```

## Examples

### Infrastructure release (v0.18.0)

**Tag annotation:**
```
v0.18.0 - Containerized Firefox Browser

Deploys a persistent Firefox browser via KasmVNC on Longhorn PVC.

Infrastructure:
- Firefox Deployment with KasmVNC web UI (lscr.io/linuxserver/firefox)
- Longhorn PVC (2Gi) for browser profile persistence
- Basic auth via K8s Secret, AdGuard DNS routing, TCP probes
- HTTPRoute at browser.k8s.rommelporras.com (LAN-only)

Documentation:
- Rebuild guide, context docs, CHANGELOG, phase plan completed
```

**GitHub release notes:**
```markdown
## Summary

Deploys a persistent Firefox browser via KasmVNC, accessible at
`browser.k8s.rommelporras.com`. Close the tab on one device, open the URL
on another - same session, same tabs. Firefox profile (bookmarks, cookies,
extensions, open tabs) persists on a Longhorn PVC. LAN-only access with
basic auth.

## What's Included

### Infrastructure
- **Firefox + KasmVNC** - `lscr.io/linuxserver/firefox` Deployment with 4Gi memory, 2Gi /dev/shm
- **Longhorn PVC** - 2Gi for browser profile persistence (bookmarks, cookies, extensions)
- **Basic auth** - CUSTOM_USER + PASSWORD injected from K8s Secret (1Password-backed)
- **AdGuard DNS routing** - `dnsPolicy: None` for ad-blocking inside the browser
- **TCP probes** - HTTP probes return 401 on unauthenticated requests; TCP avoids false unhealthy
- **HTTPRoute** - `browser.k8s.rommelporras.com` (LAN-only, not Cloudflare Tunnel)

### Integration
- Homepage dashboard entry in Apps section
- Uptime Kuma TCP monitor for availability tracking

### Documentation
- Rebuild guide: `docs/rebuild/v0.18.0-firefox-browser.md`
- Updated context files: Gateway, Cluster, Networking, Secrets

Full details: [CHANGELOG](https://github.com/rommelporras/homelab/blob/main/docs/reference/CHANGELOG.md)
```

```markdown
## Summary

Post-release fixes from Phase 4.30: GitLab Minio storage reconfiguration,

## What's Included

### Bug Fixes

Full details: [CHANGELOG](https://github.com/rommelporras/homelab/blob/main/docs/reference/CHANGELOG.md)
```

## Important rules

- NEVER release without user confirmation of the release plan (Step 7)
- Always fetch remote tags before creating a new tag
- Always use annotated tags (`git tag -a`)
- First release defaults to v0.1.0
- Release notes explain "what's in this release", not just a commit list
- Title format: always `v<VERSION> - <Short Title>` with a regular hyphen, NEVER em dash
- No em dashes anywhere in generated content
- Keep titles concise (2-4 words for the Short Title part)
- Never run git tag or gh release create commands outside of this skill execution
